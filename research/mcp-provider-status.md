# Which providers report live MCP server status?

Research for [TFordyce/t3code#4](https://github.com/TFordyce/t3code/issues/4) (map: [#1 MCP servers panel](https://github.com/TFordyce/t3code/issues/1)).
Checked against the SDK typings and generated protocol schemas pinned in this repo at `c77a7b7eeb` (2026-10-10). Versions: Codex app-server schema in `packages/effect-codex-app-server/src/_generated`, `@anthropic-ai/claude-agent-sdk` 0.3.276, ACP schema v1.21.0 and v2.0.0-alpha.3, `@opencode/*` 2.0.23 (and `@opencode-ai/sdk` 1.15.13), `@cursor/sdk` 1.0.35, `@muse-code/sdk` 1.4.2, plus T3's own Pi bridge source.

**Bottom line:** three providers report live per-session status: Codex (push and poll, the richest), Claude (poll only) and OpenCode (push signal plus poll, scoped per directory, not per session). The ACP family (Grok, Antigravity, ACP registry agents), Cursor and Muse report nothing. Pi reports whatever T3's own bridge extension chooses to report. Everything else needs the T3-side connectivity check the map already settled on.

## Recommended common vocabulary

The smallest set that every reporting provider maps onto without losing meaning, plus the T3-only states the map already requires:

| T3 status     | Codex list               | Codex push                                           | Claude       | OpenCode                                  | Meaning                                                                        |
| ------------- | ------------------------ | ---------------------------------------------------- | ------------ | ----------------------------------------- | ------------------------------------------------------------------------------ |
| `connecting`  | `notStarted`, `starting` | `starting`                                           | `pending`    | `pending`                                 | Not ready yet                                                                  |
| `connected`   | `connected`              | `ready`                                              | `connected`  | `connected`                               | Usable                                                                         |
| `needs-auth`  | `authenticationRequired` | `failed` + `failureReason: reauthenticationRequired` | `needs-auth` | `needs_auth`, `needs_client_registration` | User must log in                                                               |
| `failed`      | `failed`, `cancelled`    | `failed`, `cancelled`                                | `failed`     | `failed`                                  | Did not connect. Carry `error` text                                            |
| `disabled`    | `disabled`               | n/a                                                  | `disabled`   | `disabled`                                | Turned off                                                                     |
| `unsupported` | n/a                      | n/a                                                  | n/a          | n/a                                       | T3-only: adapter cannot carry this transport                                   |
| `unknown`     | `runtimeStatus: null`    | n/a                                                  | n/a          | n/a                                       | T3-only: provider gives no live status; show the T3 connectivity check instead |

Optional fields: `error?: string`, `toolCount?: number` (Codex and Claude only). Keep auth _method_ (Codex `authStatus`) out of the common shape; `needs-auth` is the only auth fact every reporting provider shares.

## Per-provider detail

### Codex app-server

- **Poll:** `mcpServerStatus/list` with `{ threadId?, serverName?, detail?: "full" | "toolsAndAuthOnly", cursor?, limit? }` (`_generated/schema.gen.ts`, `ClientRequest__ListMcpServerStatusParams`; method in `_generated/meta.gen.ts`). With a `threadId` it reuses that thread's MCP connection ("Limit discovery to one server. With a thread ID, reuse that thread's MCP connection.").
- **Response entry** (`V2ListMcpServerStatusResponse__McpServerStatus`): `name`, `authStatus`, `runtimeStatus?` ("Current thread-runtime connection state; null when unavailable or the configuration changed."), `tools` (map), `toolsError?`, `resources`, `resourceTemplates`, `serverInfo?`, `serverCapabilities?`, `httpOrigin?`, `pluginId?`.
- **`McpServerConnectionStatus`:** `notStarted | starting | connected | authenticationRequired | failed | cancelled | disabled`.
- **`McpAuthStatus`:** `unknown | unsupported | notLoggedIn | bearerToken | oAuth`.
- **Push:** `mcpServer/startupStatus/updated` (`ServerNotification__McpServerStatusUpdatedNotification`): `{ name, status: starting | ready | failed | cancelled, error?, failureReason?: "reauthenticationRequired", threadId? }`.
- **Auth push:** `mcpServer/oauthLogin/completed`: `{ name, success, error?, threadId? }`. Login itself is `mcpServer/oauth/login`. `config/mcpServer/reload` exists too.
- **T3 today:** `apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts` (~6361) calls `mcpServerStatus/list` with `detail: "toolsAndAuthOnly"` only to list one server's tools for MCP Apps. Nothing handles `mcpServer/startupStatus/updated` or `oauthLogin/completed`. Servers are injected per thread via `config.mcp_servers` in `codexThreadRuntimeParams` (~1318).

### Claude Agent SDK

- **Poll:** `Query.mcpServerStatus(): Promise<McpServerStatus[]>` (`sdk.d.ts` ~2835; control request subtype `mcp_status`).
- **`McpServerStatus`** (`sdk.d.ts` ~1165): `name`, `status: 'connected' | 'failed' | 'needs-auth' | 'pending' | 'disabled'`, `serverInfo?`, `error?` ("available when status is 'failed'"), `config?`, `scope?`, `source?` (`sdk | plugin | user | project | local | dynamic | managed | enterprise | claudeai | agent`), `tools?[]` with `annotations` ("available when connected").
- **Snapshot at start:** `system`/`init` message carries `mcp_servers: { name, status: string, source? }[]` and `tools: string[]` (`sdk.d.ts` ~5580). It is emitted once per query start, so it cannot show a later transition.
- **No change notification:** the `SDKMessage` union (`sdk.d.ts` ~5019) has no MCP status-change message. `setMcpServers()` returns `McpSetServersResult` with `added`, `removed` and per-server connection `errors`; `reloadPlugins` returns `mcpServers: McpServerStatus[]`. Control: `reconnectMcpServer(name)`, `toggleMcpServer(name, enabled)`.
- **T3 today:** `ClaudeAdapterV2.ts` passes `mcpServers` in query options and reads `init` only for `permissionMode` (~7462). `ClaudeAdapterV2.testkit.ts` fakes `mcp_servers: []`. No status is read.

### OpenCode

- **2.x server (T3's v2 adapter uses `@opencode/client` 2.0.23):** `GET /api/mcp` (`mcp.list`, `@opencode/protocol` `groups/mcp.d.ts`) returns `{ location: { directory }, data: { name, status, integrationID? }[] }`. `Mcp.Status` (`@opencode/schema` `mcp.d.ts`) is a tagged union: `connected | pending | disabled | failed{error} | needs_auth{error}`. No tool count.
- **Push:** `mcp.status.changed`, `mcp.tools.changed`, `mcp.resources.changed` events (`mcp-event.d.ts`), all ephemeral and carrying only `{ server }`. So: push signal, then re-list.
- **Control:** `mcp.add` / `mcp.remove` / `mcp.connect` / `mcp.disconnect` under `/api/experimental/mcp/:server`.
- **1.x SDK (`@opencode-ai/sdk` 1.15.13):** `client.mcp.status()` returns `Record<string, McpStatus>` with `connected | disabled | failed{error} | needs_auth | needs_client_registration{error}`.
- **Scope caveat:** status is per OpenCode server and directory, not per session. `packages/provider-opencode/src/server/v2/adapter.ts` (~450) already notes that T3's MCP server "is registered per directory, not per session". A user server added once per directory serves every OpenCode session in that directory.
- **T3 today:** the v2 adapter calls `client.mcp.add` / `remove` for `t3-code` only (~3227-3290). It does not read `mcp.list` or the status events.

### ACP (Grok, Antigravity, ACP registry agents)

- `packages/effect-acp/src/_generated/schema-v1.gen.ts` (v1.21.0) and `schema.gen.ts` (v2.0.0-alpha.3): MCP appears only as `McpServer` config on `session/new` / `load` / `resume`, the `McpCapabilities` flags `{ http, sse, acp }`, and the unstable MCP-over-ACP transport (`mcp/connect`, `mcp/message`, `mcp/disconnect`). No method or `sessionUpdate` kind reports server status (`meta.gen.ts` method list; `sessionUpdate` kinds are message/thought/tool/plan/mode/config/usage/compaction/session-info).
- **Grok:** `packages/provider-grok/src/server/xaiAcpExtension.ts` handles `_x.ai/session/update`, `_x.ai/task_*`, `x.ai/exit_plan_mode`, `x.ai/ask_user_question`. None of them carry MCP status. The Grok CLI is not installed on this machine, so its binary was not checked for undocumented extensions.
- **Antigravity:** `AntigravityAdapterV2.ts` runs the shared `AcpSessionRuntime`. Nothing beyond ACP.
- **One useful signal:** for the `acp` MCP transport (T3 hosts the server over the ACP channel), `handleMcpConnect` / `Disconnect` in `packages/provider-acp/src/server/AcpSessionRuntime.ts` tell T3 when the agent actually opened `t3-code`. That is T3-observed, not agent-reported, and covers only servers T3 itself serves.

### Cursor

- `@cursor/sdk` 1.0.35: `McpServerConfig` (stdio or http/sse with optional OAuth `auth`) goes in through `mcpServers`. `SDKSystemMessage` (`messages.d.ts`) is `{ subtype?: "init", agent_id, run_id, model?, tools?: string[] }`. `SDKStatusMessage` is run lifecycle (`CREATING | RUNNING | FINISHED | ERROR | CANCELLED | EXPIRED`), not MCP. MCP shows up only as tool calls (`type: "mcp"`). No status API.

### Pi

- Pi has no native MCP client. `packages/provider-pi/src/server/mcpExtensionSource.ts` is a T3-written Pi extension that connects to T3's HTTP MCP server, calls `tools/list`, and registers the tools. On failure it calls `ctx.ui.notify("t3-code MCP unavailable: …", "warning")`, which the Pi adapter turns into a `notify` activity item (`adapter.ts` ~1216).
- Extending the bridge to user servers would make T3 the MCP client, so T3 owns the status. It could report status through the same RPC `extension_ui_request` channel or a dedicated custom event. This is a design choice, not a provider capability.

### Muse (MSP, not in ticket scope)

- `@muse-code/sdk` 1.4.2 `msp.d.ts`: `SessionMcpServerConfig` with `mode: "required" | "optional"`. A required server that fails to start fails `session/start`. There is no live status method or event.

## Implications for the panel

1. A per-session live status column is feasible for Codex and Claude, and per-directory for OpenCode. Every other adapter reports `unknown` and falls back to the T3 connectivity check.
2. Codex is the only provider that pushes real transitions. Claude needs a poll (for example, after `init` and when the panel opens). OpenCode needs a re-list on `mcp.status.changed`. Poll only while a panel is open to avoid websocket churn.
3. `ProviderRuntimeMcpStatusUpdatedEvent` (`mcp.status.updated`, payload `status: Unknown`) and `mcp.oauth.completed` already exist in `packages/contracts/src/providerRuntime.ts` (~192, 716, 1084) but nothing emits them. Give the first a typed payload in the common vocabulary instead of adding a new event.
4. Codex `cancelled` and OpenCode `needs_client_registration` are folded into `failed` and `needs-auth`. Keep the raw provider value in `error` or a detail string if debugging needs it.
